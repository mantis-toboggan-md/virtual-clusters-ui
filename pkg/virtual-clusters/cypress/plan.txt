Plan: add Cypress e2e tests to the virtual-clusters extension
================================================================

Goal
----
Add an e2e suite (mirroring rancher/dashboard's Cypress conventions, no code
imported from that repo) exercising the extension in a real Rancher instance.
Run it in CI on PRs and on merge to main.

Current state
--------------
- pkg/virtual-clusters/cypress/ is empty. No cypress/test scripts anywhere
  in the repo. Root package.json has build-pkg/serve-pkgs/publish-pkgs/lint.
- .github/workflows/ has no lint/test workflow to copy from.
- k3k card is registered in pkg/virtual-clusters/provisioner.ts (label via
  i18n key 'k3k.label'); the card is rendered by dashboard's cluster-creation
  page, not this extension, and has no data-testid we control.

1. Cypress test setup (repo root)
----------------------------------
- cypress.config.ts + cypress/ dir at repo root (alongside build-pkg/
  serve-pkgs), not under pkg/virtual-clusters.
- Layout mirroring dashboard's conventions, own implementation:
    cypress/e2e/tests/**      - specs, grouped by feature
    cypress/e2e/po/           - page objects (LoginPo, ClusterCreatePo, ...)
    cypress/support/commands  - custom commands (cy.login, etc.)
    cypress/e2e/blueprints/   - fixtures, as needed
- Selectors: reuse dashboard's existing data-testid values where its pages
  render them. The k3k card has none, so select it by its rendered
  translated label text instead.
- Env params:
    - TEST_USERNAME / TEST_PASSWORD (or CATTLE_BOOTSTRAP_PASSWORD) - admin
      login
    - TEST_BASE_URL - Rancher dashboard URL, required
    - EXTENSION_URL - served extension URL, optional; when absent, skip
      creating the uiplugins resource and assume the extension is already
      loaded
- Initial spec: log in as admin, go to cluster creation, assert a card
  labeled "k3k" is present (text-based selector). Get this green in CI
  before adding more coverage.
- Add cy:open / cy:run / e2e:ci scripts to root package.json.

2. CI workflow
--------------
- New .github/workflows/e2e.yml, triggered on pull_request (any branch ->
  main) and push to main. No separate approval-gated environment - a normal
  pull_request trigger, required via branch protection.
- Prime images come from the alpha channel:
      helm repo add rancher-alpha \
        https://charts.optimus.rancher.io/server-charts/alpha
  This is required, not a preference: the extension is annotated
  prime-only, and Rancher refuses to load a prime-only extension unless the
  server reports RancherPrime=true (see dashboard
  shell/config/uiplugins.js shouldNotLoadPlugin + shell/config/version.js
  isRancherPrime, which reads the backend /rancherversion API). On a
  community rancher/rancher image the extension silently never loads and
  the k3k card never appears.
    - This channel carries alphas for every minor line we need, so it is
      the single source for all matrix rows. The per-line optimus channels
      (server-charts/release-2.14 etc.) are NOT prime and cannot be used
      here, even though dashboard's own compatibility workflow points at
      them - don't reach for them as a fallback.
    - Consequence: do NOT override the chart's image with the community
      one. dashboard's e2e-extension-k3s-start.sh defaults to
      rancher/rancher:head on Docker Hub and passes
      --set image.repository/--set image.tag, which would undo the prime
      image. Either drop those overrides and let the alpha chart's own
      default image apply, or point them explicitly at the prime image.
      Note systemDefaultRegistry only covers system/agent images, not the
      server image.
- Version manifest: new file (e.g. rancher-versions.json) at repo root,
  keyed by the PR's *base* branch (github.base_ref) - not the head branch,
  which won't be a manifest key on a PR. All rows share the one alpha repo
  URL, so each row pins a chart version rather than a per-line channel:
    { "main": [
        { "chartVersion": "2.16.0-alphaN", "kubeVersion": "v1.36.x+k3s1" },
        { "chartVersion": "2.15.x-alphaN", "kubeVersion": "v1.35.x+k3s1" },
        { "chartVersion": "2.14.x-alphaN", "kubeVersion": "v1.35.x+k3s1" } ] }
  kubeVersion is required per row (the k3s version must match what that
  Rancher version supports; dashboard's script hard-fails without it).
  Workflow reads this into a matrix so adding/removing tested versions
  doesn't require editing the workflow.
- Per matrix entry:
    - stand up k3s + the matching Rancher version (adapt, don't import,
      dashboard's e2e-extension-k3s-start.sh pattern). Pass --version
      $chartVersion to helm install alongside the existing --devel; the
      script pins no version today, so against a single alpha channel all
      three rows would otherwise install the same newest alpha and the
      matrix would collapse to three identical runs.
    - bring up a k3d cluster and import it into Rancher as a generic
      cluster, scripted headlessly (net new - dashboard's workflows only
      stand up the k3s host cluster; its own import test drives the UI):
        1. create the cluster: POST /v3/clusters with
           { type: 'cluster', name: <name>, agentEnvVars: [],
             importedConfig: {}, labels: {},
             annotations: { 'rancher.io/imported-cluster-version-management':
                            'system-default' } }
        2. resolve the management cluster name (the c-m-xxxxx id) from the
           created cluster
        3. GET /v1/management.cattle.io.clusterregistrationtoken from the
           local cluster, in the namespace named after the management
           cluster name, and read 'command' / 'insecureCommand' off the
           token
        4. run that command (use insecureCommand for the self-signed CI
           cert) against the k3d cluster's kubeconfig
      Note: dashboard's UI uses the Norman /v3/clusterregistrationtokens
      path instead, so it's not a copyable precedent for step 3 - confirm
      the exact field location on the v1 resource against a live cluster
      when implementing.
    - bootstrap admin login (curl loop against v3-public, same as
      dashboard)
- Extension under test: yarn build-pkg, serve-pkgs, then create the
  catalog.cattle.io.uiplugins resource directly via the Rancher API
  pointing at the served URL (skip dashboard's UI-driven "Developer Load").
- Login params for CI: admin only for now (TEST_USERNAME=admin, password
  from CATTLE_BOOTSTRAP_PASSWORD). Multi-role coverage is out of scope.
